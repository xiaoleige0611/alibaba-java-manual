# 第 12 章：异常日志 —（一）错误码 + 附 3 错误码列表（泰山版新增）

## Core Idea
泰山版（v1.6.0）**首次发布错误码统一解决方案**。错误码只回答两个问题：**是谁的错？错在哪？** 因此它必须能快速溯源、简单易记、便于沟通，而不是追求完美的分类体系。格式统一为“来源字母 A/B/C + 四位数字”的 5 位字符串，并配一张全公司共享的错误码表（附 3）。

## Frameworks Introduced
- **错误码制定三原则**（【强制】）：快速溯源（一眼知道是谁的问题）、简单易记（便于记忆和比对，代码里容易 equals）、沟通标准化（脱离文档和系统平台也能线下轻量沟通）。
  - 反面比喻：设计得过于完美复杂的错误码，就像康熙字典里的生僻字，用词精准，但字典既不便携也不好懂。
- **5 位错误码结构**：`来源(1 位字母) + 编号(4 位数字)`，类型是字符串。
  | 来源 | 含义 | 例子 |
  |---|---|---|
  | **A** | 错误来源于用户 | 参数错误、安装版本过低、支付超时 |
  | **B** | 错误来源于当前系统 | 业务逻辑出错、程序健壮性差 |
  | **C** | 错误来源于第三方服务 | CDN 出错、消息投递超时 |
  - 编号 0001–9999，大类之间的步长预留 100。
  - 全部正常但必须填错误码时，返回 `00000`。
- **三级宏观错误码**（【参考】）：一级 `A0001` 用户端错误 / `B0001` 系统执行出错 / `C0001` 调用第三方服务出错；二级如 `C0100` 中间件服务出错；三级如 `C0120` 消息服务出错。无法确定更具体的场景时，可以直接用一级码。
- **四件套各司其职**：堆栈（stack_trace）、错误信息（error_message）、错误码（error_code）、提示信息（user_tip）相互关联、可以互相转义，但不能互相替代。
- **第三方错误码转义**（【推荐】）：拿到第三方服务的错误码时向上抛出，允许本系统把 C 类转义为 B 类，同时在错误信息里带上原始的第三方错误码。

## 规约速查
> 编号为泰山版二、异常日志（一）错误码中的编号；整节为泰山版新增。

| # | 级别 | 规则 |
|---|---|---|
| 1 | 强制 | 制定原则：快速溯源、简单易记、沟通标准化 |
| 2 | 强制 | 错误码**不体现版本号和错误等级**：以不断追加的方式兼容；等级由日志和错误码释义决定 |
| 3 | 强制 | 全部正常但不得不填错误码时，返回 `00000` |
| 4 | 强制 | 错误码为 5 位字符串：A/B/C 来源 + 四位数字编号（0001–9999，大类步长 100） |
| 5 | 强制 | 编号不与公司业务架构、组织架构挂钩；在平台上先到先申请，审批生效后永久固定 |
| 6 | 强制 | 使用者避免随意定义新错误码，尽量在已有附表中找语义相同或相近的码 |
| 7 | 强制 | **错误码不能直接输出给用户作为提示信息** |
| 8 | 推荐 | 错误码之外的业务独特信息由 error_message 承载，不要让错误码本身包含过多业务属性 |
| 9 | 推荐 | 第三方错误码向上抛出时可由 C 转义为 B，错误信息中带上原始错误码 |
| 10 | 参考 | 错误码分一级、二级、三级宏观错误码 |
| 11 | 参考 | 错误码后三位编号与 HTTP 状态码**没有任何关系** |
| 12 | 参考 | 错误码要便于不同文化背景的开发者协作：英文单词形式的错误码对非英语母语开发者不友好 |
| 13 | 参考 | 纯数字错误码不利于感性记忆和分类（人脑不会主动区分 `12345` 中每一位的含义） |

## Key Concepts
- **一级宏观错误码**：`A0001`、`B0001`、`C0001`，分别对应用户端、当前系统、第三方的笼统错误。
- **二级宏观错误码**：每个大类下按 100 步长划分的子类，如 `A0400` 用户请求参数错误。
- **error_message**：承载错误码以外的具体业务信息。
- **user_tip**：给用户看的提示文案，与错误码分离。
- **转义**：把第三方（C）错误包装成本系统（B）错误继续上抛。

## Mental Models
- **错误码是“谁的锅”标签**：看到首字母就能分派——A 找前端或用户，B 找自己，C 找下游。
- **错误码只增不改**：它是对外契约，像二方库版本一样，追加兼容，不重新编号（对照 ch09 二方库规约）。
- **码给机器和工程师看，提示给用户看**：用户界面上永远显示 user_tip，不显示 `B0001`。

## Anti-patterns
- 用 `40001` 这类纯数字码，再规定“第 1 位是等级、第 2 位是来源”：人记不住每一位的含义。
- 错误码里编码版本号或错误等级：升级时被迫改码，破坏兼容性。
- 按部门或组织架构分配号段：组织一调整，号段就失去意义。
- 每个团队各自新建语义重复的错误码：同一个“参数为空”有十几个码。
- 把 `A0410` 直接弹给用户看。
- 以为 `A0404` 和 HTTP 404 有关系。

## Code Examples
```java
// 错误码枚举 + Result 返回（根据规则写的示意，原文没有代码）
public enum ErrorCode {
    /** 一切 ok */
    SUCCESS("00000"),
    /** 请求必填参数为空 */
    PARAM_REQUIRED("A0410"),
    /** 系统执行超时 */
    SYSTEM_TIMEOUT("B0100"),
    /** RPC 服务出错 */
    RPC_ERROR("C0110");

    private final String code;   // 字符串类型，5 位
    ErrorCode(String code) { this.code = code; }
    public String getCode() { return code; }
}

// 第三方错误转义：C → B，并保留原始错误码
catch (ThirdPartyException e) {
    logger.error("call pay channel failed, req={}, thirdCode={}", req, e.getCode(), e);
    return Result.fail(ErrorCode.SYSTEM_TIMEOUT, "pay channel timeout, thirdCode=" + e.getCode());
}
```
- **What it demonstrates**：错误码是字符串；枚举每一项都有注释（ch05）；第三方错误转义时保留原码；user_tip 另行生成，不直接用错误码。

## Worked Example
给“用户下单”接口设计错误码映射：
1. 订单号为空 → 用户错误，`A0411 用户订单号为空`；只有在附表里找不到合适的码时才申请新码（第 6 条）。
2. 购买数量超过限制 → `A0425 数量超出限制`；具体上限值放在 error_message 里，例如 `"max=99"`（第 8 条）。
3. 本系统订单处理超时 → `B0101`。
4. 调用支付渠道超时 → 下游原始码为 `C0200` 类；对上游接口可以转义成 B 类，并在 error_message 里带上原码（第 9 条）。
5. 接口返回 `Result{ success=false, errorCode="A0411", errorMessage="orderId is empty" }`，前端根据错误码映射出 user_tip，例如“请填写订单号”，不直接展示 A0411（第 7 条）。
6. 成功时如果协议要求必须有错误码，就填 `00000`（第 3 条）。
7. 不要因为接口升级到 v2 就改错误码，也不要让码里包含“严重等级”（第 2 条）。

## Key Takeaways
1. 错误码 = A/B/C 来源 + 4 位数字，类型是字符串；成功时用 `00000`。
2. 首字母定责：A 用户、B 本系统、C 第三方；第三方错误可以转义为 B 并保留原码。
3. 不编码版本号和等级，不挂钩组织架构，申请后永久固定，只追加不修改。
4. 优先复用附表中的码；业务细节放 error_message；用户看 user_tip。
5. 后三位与 HTTP 状态码无关。
