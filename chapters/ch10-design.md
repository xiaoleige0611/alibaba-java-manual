# 第 10 章：设计规约

## Core Idea
设计的本质是**识别和表达系统难点，找到变化点并隔离它**。手册用一组**数量阈值**规定什么时候必须画哪种 UML 图，要求存储方案必须经过评审，并用 SOLID 中的几条原则（单一职责、里氏代换、依赖倒置、开闭原则）以及“组合优于继承”来约束类的设计。

## Frameworks Introduced
- **UML 触发阈值**（全部为【强制】）：
  | 条件 | 必须画的图 | 要明确的内容 |
  |---|---|---|
  | 交互的 User 超过 1 类，且相关的 User Case 超过 5 个 | **用例图** | 结构化的需求 |
  | 某个业务对象的状态超过 3 个 | **状态图** | 两两状态之间能否直接转换，以及触发转换的条件 |
  | 某个功能的调用链路涉及的对象超过 3 个 | **时序图** | 每个调用环节的输入与输出 |
  | 模型类超过 5 个，且存在复杂的依赖关系 | **类图** | 类之间的关系 |
  | 超过 2 个对象之间有协作关系，且处理流程复杂 | **活动图** | 带对象泳道的流程，支持表示并发 |
- **存储方案评审**（【强制】）：评审内容包括存储介质选型、表结构能否满足技术方案、存取性能和存储空间能否满足业务发展、表或字段之间的关系、字段名称、字段类型、索引等；**数据结构变更（如新增字段）同样要评审通过后才能上线**；提交生产环境执行后要做 double check。
- **类设计原则**（【推荐】）：
  - **单一原则**：最容易理解，却最难做到，随着系统演进很容易忘记类设计的初衷。
  - **组合或聚合优于继承**：不得已使用继承时，必须符合**里氏代换原则**（父类能出现的地方，子类一定能出现，例如“把钱交出来”，美元、欧元、人民币都可以）。
  - **依赖倒置**：依赖抽象类与接口；低层模块依赖高层模块的抽象。
  - **开闭原则**：对扩展开放，对修改关闭；同一业务域内的需求变化，通过扩展模块或类来实现。
  - **抽取共性**：公共模块、公共配置、公共类、公共方法；代码重复次数越多，维护成本呈指数级上升。
- **系统架构设计的四个目的**（【参考】）：确定系统边界（技术层面做什么、不做什么）；确定模块之间的关系（依赖、宏观输入与输出）；确定指导后续设计与演化的原则；确定非功能性需求（安全性、可用性、可扩展性等）。
- **无障碍设计**（【参考】）：所有可交互控件都能被 tab 键聚焦，焦点顺序符合自然操作逻辑；用于登录校验和请求拦截的验证码要提供图形验证以外的方式；自定义控件要明确交互方式。

## Key Concepts
- **变化点**：系统中最可能随需求变化的部分；所有设计模式的共同目的都是隔离变化点。
- **里氏代换原则（LSP）**：子类必须能替换父类。
- **依赖倒置原则（DIP）**：依赖抽象，而不是具体实现。
- **开闭原则（OCP）**：通过扩展来应对变化，而不是修改已有代码。
- **泳道**：活动图中表示由哪个对象负责某一步的分区。

## Mental Models
- **类图就像施工图**：搭平房可能不需要，建大楼一定需要（模型类超过 5 个就画）。
- **状态图先问三件事**：一共有多少种状态？哪两个状态之间能直接转换？转换由什么触发？
- **异常流程和主干流程同样重要**：设计时只考虑顺利的路径，上线后出问题的往往是异常路径。
- **敏捷不等于不做设计**：可以省掉多余的设计和审批，但关键节点上必要的设计和文档不能省。

## Anti-patterns
- 用户付款时银行扣款成功并发了短信，支付宝入账却因断网演练失败，订单页面仍显示未付款，导致用户投诉 → 没有评估异常流程。
- “敏捷”成了产品经理催进度的借口，代码像面条一样，一年后不得不大规模重构。
- 为了复用而继承，子类却无法替换父类（违反 LSP）。
- 生产环境新增字段不经评审就直接执行。
- 为了设计而设计：设计文档写完就丢，不归档，后期维护时没人看。

## Code Examples
```java
// 开闭原则 + 依赖倒置：新增支付方式只需要新增实现类，不修改调用方（根据规则写的示意）
public interface PayChannel {
    Result pay(PayRequest request);
}
public class AlipayChannel implements PayChannel { ... }
public class WechatChannel implements PayChannel { ... }

public class PayService {
    private final Map<String, PayChannel> channels;   // 依赖抽象
    public Result pay(String type, PayRequest req) {
        return channels.get(type).pay(req);
    }
}
```
- **What it demonstrates**：隔离变化点（支付渠道），对扩展开放、对修改关闭。

## Worked Example
设计一个订单系统前，按阈值检查需要哪些图：
1. 用户类型有买家、卖家、客服 3 类，用例包括下单、付款、发货、退款、评价、投诉等 6 个以上 → 画**用例图**。
2. 订单状态有已下单、待付款、已付款、待发货、已发货、已收货等 6 种（超过 3 种）→ 画**状态图**，并写明“已下单不可能直接变成已收货”这类约束以及触发条件。
3. 下单链路涉及订单、库存、优惠、支付 4 个对象（超过 3 个）→ 画**时序图**，标注每一步的输入和输出。
4. 模型类有 Order、OrderItem、Sku、Coupon、Payment、Address 等 6 个以上 → 画**类图**。
5. 退款流程需要买家、客服、财务 3 方协作 → 画**活动图**，用泳道表示各方负责的步骤。
6. 订单表结构和索引设计提交评审，通过后才能上线；以后新增字段也要走评审（第 1 条，结合 ch08 建表规约）。
7. 专门列出异常流程：支付回调超时、重复回调、库存扣减失败的补偿等（第 7 条）。

## Key Takeaways
1. 存储方案和数据结构（包括后续变更）必须评审通过，并沉淀成文档。
2. 记住阈值：用例超过 5 个画用例图；状态超过 3 个画状态图；调用链对象超过 3 个画时序图；模型类超过 5 个画类图；协作对象超过 2 个画活动图。
3. 设计时同时评估异常流程和业务边界。
4. 遵守单一职责、组合优于继承（符合里氏代换）、依赖倒置、开闭原则。
5. 设计的本质是找到变化点并隔离它；架构设计要确定边界、模块关系、演化原则和非功能需求。
