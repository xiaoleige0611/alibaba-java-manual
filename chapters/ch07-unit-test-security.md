# 第 7 章：单元测试 + 安全规约

## Core Idea
好的单元测试像空气一样：线上运行时感觉不到它的存在，却是质量的关键保障 —— 这就是 **AIR 原则**；测试用例的设计则遵循 **BCDE 原则**。安全规约的出发点是**用户传入的一切都不可信**：要做权限校验、数据脱敏、参数绑定、输入校验、输出转义、CSRF 防护和防重放。

## Frameworks Introduced
- **AIR 原则**（【强制】）：
  - **A — Automatic（自动化）**：全自动、非交互式执行；必须用 assert 验证，**禁止用 System.out 人工检查**。
  - **I — Independent（独立性）**：用例之间不能互相调用，也不能依赖执行的先后顺序。
  - **R — Repeatable（可重复）**：不受网络、服务、中间件等外部环境影响；把被测对象（SUT）的依赖改成注入，测试时注入内存实现或 Mock 实现。
- **BCDE 原则**（【推荐】）：
  - **B — Border**：边界值测试，包括循环边界、特殊取值、特殊时间点、数据顺序。
  - **C — Correct**：正确的输入，得到预期的结果。
  - **D — Design**：结合设计文档编写测试。
  - **E — Error**：强制输入错误信息（非法数据、异常流程、业务不允许的情况），得到预期的结果。
- **覆盖率目标**：语句覆盖率达到 **70%**；核心模块的语句覆盖率和分支覆盖率都要达到 **100%**。DAO 层、Manager 层和可重用度高的 Service 都应该写单元测试。
- **可测性四忌**：构造方法做的事情过多、全局变量和静态方法过多、外部依赖过多、条件语句过多（多层条件用卫语句、策略模式、状态模式重构）。
- **输入校验六大风险**（安全 4）：page size 过大导致内存溢出、恶意 order by 导致慢查询、任意重定向、SQL 注入、反序列化注入、ReDoS（正则拒绝服务）。

## 规约速查
| # | 级别 | 规则 |
|---|---|---|
| UT1 | 强制 | 遵守 AIR 原则 |
| UT2 | 强制 | 全自动、非交互；用 assert，禁用 System.out |
| UT3 | 强制 | 用例之间相互独立 |
| UT4 | 强制 | 可重复执行，不依赖外部环境 |
| UT5 | 强制 | 粒度足够小：最多到类级别，一般是方法级别；跨类、跨系统的交互属于集成测试 |
| UT6 | 强制 | 核心业务、核心应用、核心模块的增量代码必须通过单元测试 |
| UT7 | 强制 | 测试代码放在 `src/test/java` |
| UT8 | 推荐 | 语句覆盖率 70%，核心模块 100% |
| UT9 | 推荐 | 遵守 BCDE 原则 |
| UT10 | 推荐 | 不假设数据库里已有数据，用程序插入或导入数据，不手工往库里插 |
| UT11 | 推荐 | 数据库相关测试设置自动回滚，或给测试数据加明确的前后缀 |
| UT12 | 推荐 | 不可测的代码要重构，不要为了达标写不规范的测试 |
| UT13 | 推荐 | 设计评审阶段，开发与测试一起确定单元测试范围 |
| UT14 | 推荐 | 提测前完成单元测试，不要等发布后再补 |
| SEC1 | 强制 | 属于用户个人的页面或功能必须做权限校验（**水平越权**） |
| SEC2 | 强制 | 用户敏感数据要脱敏展示（手机号显示为 `137****0969`） |
| SEC3 | 强制 | SQL 参数用参数绑定或 METADATA 字段值限定，**禁止拼接 SQL** |
| SEC4 | 强制 | 用户传入的任何参数都要做有效性校验 |
| SEC5 | 强制 | 不向 HTML 页面输出未经安全过滤或转义的用户数据（XSS） |
| SEC6 | 强制 | 表单和 AJAX 提交必须做 **CSRF** 验证 |
| SEC7 | 强制 | 短信、邮件、电话、下单、支付等平台资源必须有防重放机制：数量限制、疲劳度控制、验证码校验 |
| SEC8 | 推荐 | 发帖、评论、即时消息等用户生成内容要做防刷和违禁词过滤 |

## Key Concepts
- **SUT（System Under Test）**：被测系统或对象。
- **集成测试**：负责跨类、跨系统的交互逻辑，单元测试不负责这部分。
- **水平权限校验**：校验当前用户只能操作属于自己的数据。
- **CSRF**：跨站请求伪造，攻击者事先构造好 URL，受害者一访问，后台就在用户不知情的情况下修改了数据。
- **ReDoS**：特殊构造的输入让正则表达式陷入回溯，近似死循环。
- **防重放**：防止同一个请求或资源被反复滥用。

## Mental Models
- **测试不能需要人看**：只要需要人去看输出结果，这个测试就失去了自动化的意义。
- **依赖要能注入**：如果一个类没法 Mock，问题出在设计，不在测试。
- **把每个入参都当成攻击载荷**：page size、order by、重定向地址、正则输入源都可能被利用。
- **每个会花钱的接口都要有闸门**：短信、支付等接口必须有频率和数量限制，否则会被刷导致资损。

## Anti-patterns
- method2 依赖 method1 的执行结果作为输入：违反独立性。
- 手工往数据库插一行再测删除：插入的数据不符合业务规则，测试结果异常。
- 单元测试依赖真实的网络或中间件：持续集成频繁失败。
- 发送验证码不限次数和频率：被用来骚扰他人，浪费短信资源。
- 对单元测试的四种误解：那是测试同学的事；单元测试代码是多余的；单元测试代码不需要维护；单元测试和线上故障没关系。

## Code Examples
```java
// 正例：用 assert 验证，依赖注入 Mock，测试数据带前缀，自动回滚
@Transactional   // 测试结束后自动回滚，不留脏数据
@Rollback
public class UserServiceTest {
    private static final String PREFIX = "ENTERPRISE_INTELLIGENCE_UNIT_TEST_";

    @Test
    public void testRegister_nameTooLong_returnsError() {   // E：错误输入
        Result r = userService.register(PREFIX + longName);
        assertFalse(r.isSuccess());
    }
}

// 安全：参数绑定（MyBatis 用 #{}，不用 ${}）
SELECT id, name FROM user WHERE id = #{id}
```

## Worked Example
给“查询我的订单（分页）”接口做安全审查加测试设计：
1. **权限**：SQL 必须带 `user_id = 当前登录用户`，否则可以通过修改 orderId 查看他人的订单（SEC1）。
2. **脱敏**：返回结果中的收货手机号显示为 `137****0969`（SEC2）。
3. **校验**：pageSize 设上限（比如 ≤ 100）；sort 字段只允许白名单中的值，防止恶意 order by（SEC4）；SQL 使用 `#{}`（SEC3）。
4. **测试用例（BCDE）**：B — pageSize 为 0、1、100、101，第一页和最后一页；C — 正常查询返回自己的订单；D — 按设计文档覆盖各种状态筛选；E — 传入他人的 userId、非法的 sort 字段，预期被拒绝。
5. **AIR**：订单 DAO 用 Mock 注入，测试数据加前缀并自动回滚，所有结果用 assert 验证。

## Key Takeaways
1. 单元测试遵守 AIR：自动化（用 assert）、独立、可重复（依赖注入加 Mock）。
2. 用例设计遵守 BCDE：边界、正确、设计、错误。
3. 覆盖率：语句 70%，核心模块的语句和分支都要 100%；测试代码放在 `src/test/java`。
4. 不可测就重构：避免构造方法过重、静态方法过多、外部依赖过多、条件分支过多。
5. 安全七条强制规约：水平权限、脱敏、参数绑定、输入校验、输出转义、CSRF、防重放。
